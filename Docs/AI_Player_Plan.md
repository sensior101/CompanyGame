# AI 플레이어 계획

기준: 2026-10-13 `Dev`. 솔로·소규모 방(2~20명)을 AI 플레이어로 채워 사람과 하는 것처럼 즐기게 하는 계획입니다. **서버 비용을 늘리지 않는 것**이 전제입니다.

이 문서만 보고 다른 세션에서 이어서 작업할 수 있게 썼습니다. 코드 사실은 2026-10-12~13에 직접 확인한 것이고, 파일 경로는 `CompanyGame/Assets/Scripts/` 기준입니다(서버는 `Server/`).

---

## 0. 정한 방향 (다시 논의하지 않음)

| 항목 | 결정 |
| --- | --- |
| AI 방식 | **규칙 기반 Utility AI.** 행동마다 `점수 = 상황(돈, 시세, 시간, 관계) × 성향 + 랜덤`을 매기고, 1등만이 아니라 점수 비율 확률로 고릅니다. LLM은 쓰지 않습니다(호출 요금). 자유 대화는 나중에 선택 옵션으로만 검토합니다. |
| 판마다 다른 플레이 | 월드를 만들 때 시드를 뽑아 봇마다 성향 수치(탐욕, 위험선호, 사교성, 인내심 등)와 **목표 타입**(부동산왕, 주식 단타, 회사 키우기, 사교형 거래꾼, 사기꾼형, 짠돌이 등 6~8종), 이름·외형·말투를 정합니다. 방이 여러 개여도 같은 전개가 나오지 않습니다. |
| 20명이 다 다르게 보이기 | 수치만 다르면 비슷해 보입니다. 목표 타입 + 일과 패턴 + 말투 + 실수 확률·반응 속도를 다르게 둡니다. 현실적인 구성은 "눈에 띄는 봇 5~8명 + 배경 역할 봇"입니다. |
| 같은 규칙 | **봇은 플레이어와 같은 행동 함수만 호출합니다.** 봇 전용 경제 코드는 만들지 않습니다. 새 기능이 생기면 봇 쪽에는 그 행동의 점수 계산만 추가합니다. |
| 두뇌와 몸체 분리 | **두뇌(백단)는 방장 PC**: 모든 봇의 판단, 봇 데이터, 사람 없는 맵의 봇 이동. **몸체는 실제 사람이 있는 맵에서만** 만들고, 그 맵에 있는 사람 중 1명(**맵 담당**)이 움직이며 위치를 보냅니다. 방장인지와 상관없습니다. 시민 NPC와 자동차도 같은 방식입니다. |
| 결과 확정 | 봇 행동도 op로 보내 **서버가 순서를 매기고 모든 PC가 같은 검사로 적용**합니다(지금 유저 행동과 같은 경로). 봇과 유저가 같은 땅을 동시에 사도 한 명만 성공합니다. 방장 유저가 직접 누르는 게 아니라 방장 PC 프로그램이 자동으로 보냅니다. |
| 방장 이탈 | 기존 방장 넘기기(`NetSession.TransferHost`, `NetWorldBridge`의 인계 흐름)로 새 방장 PC가 봇 두뇌를 이어받습니다. 봇 상태는 월드 스냅샷에 있어야 합니다. |
| 관계 점수 | **봇↔유저, 봇↔봇**만 기록합니다(최대 20×20 + 20×19 ≈ 780개). 0이 아닌 값만 저장하고, 시간이 지나면 0으로 천천히 돌아갑니다. 유저↔유저는 기록하지 않습니다. |
| 캐릭터 구조 | 사람(플레이어, 시민, AI 플레이어, 원격 아바타)은 모두 **`CharacterProfile`(데이터) + `CharacterBody`(몸체)** 하나의 구조를 씁니다. 관계 점수는 Profile에 넣지 않고 별도 표로 둡니다. |
| 확장 방식 | 새 기능은 Profile에 **필드를 직접 추가**합니다. `JsonUtility`는 옛 세이브에 없는 필드를 기본값으로 채우므로 기존 세이브가 깨지지 않습니다. "아무 스탯이나 담는 범용 딕셔너리"는 만들지 않습니다(오타가 안 잡히고 디버깅이 어려움). |
| 보안 수준 | 친구끼리 하는 수준의 신뢰 모델입니다(7절). 공개 매칭·랭킹·유료 결제가 생기면 **돈 관련 op만 서버가 검증**하는 방식으로 넘어갑니다(이때 서버 비용 조금 발생). |
| 시기 | 기반(1단계)은 지금, 봇 데이터(2단계)는 주요 경제 기능이 자리 잡은 뒤, AI 판단·대사(3단계)는 맵·기능이 거의 완성된 뒤에 합니다. 판단 로직은 기능·맵이 바뀌면 같이 고쳐야 하므로 미리 만들지 않습니다. |

## 1. 지금 구조 (작업 전 알아야 할 사실)

### 네트워크
- 서버(`Server/`)는 **중계만** 합니다. 로컬 Node(`src/`, 친구와 할 때는 cloudflared 터널)와 Cloudflare Worker(`worker/`, Durable Object `Lobby`) 두 형태가 있습니다. 게임 시뮬레이션은 Unity 쪽에서 합니다.
- 메시지 종류(`Server/src/protocol.ts`, `src/rooms.ts`):
  - `pos`: 각 플레이어 위치. 맵 경로가 들어 있습니다(`NetSession.SendPos(map, pos, ry, speed)`, `Player/NetPlayerSync.cs`가 0.1초마다 전송). **그래서 모든 PC가 누가 어느 맵에 있는지 압니다.**
  - `world`: **방장만 보낼 수 있습니다**(`rooms.ts` `relayWorld` → `hostRoom(peer)`). 저장되지 않는 실시간 데이터(시계, 시민, 자동차)입니다. 방 전체에 보내고, 받는 쪽이 맵으로 거릅니다. 개수 제한 버킷이 없습니다.
  - `op`: 누구나 보낼 수 있습니다. 서버가 `seq`와 `from`(로그인 계정 ID)을 붙여 보낸 사람 포함 모두에게 보냅니다. **연결당 초당 10개 제한**(`OP_PER_SEC = 10`)이 있습니다.
  - `state`: 방장의 전체 스냅샷, 최대 512KB(`MAX_STATE`), 약 10초마다 보냅니다(`NetSession.SnapshotInterval`).
  - `msg`: 1:1 메시지. 방장은 누구에게나, **참가자는 방장에게만** 보낼 수 있습니다(`rooms.ts` `relayMsg`). 방장 인계에 씁니다.
  - 채팅용 메시지는 없습니다(1-4b).
  - 그 밖의 한도: `pos` 30/초, `msg` 60/초, 메시지 한 개 최대 8KB(`MAX_MSG`, state 제외).
- 공용 월드 변경 흐름: 매니저의 `Try*` → `SharedWriteGate.TrySend` → op 전송 → 에코 수신 → `Gameplay/WorldOps.Apply`가 모든 PC에서 같은 순서로 적용합니다. 방에 없으면 게이트가 열려 바로 로컬에 씁니다.
- `WorldOps.ActorMatches`가 op 안의 행위자 필드(`a.b` 또는 `a.c`)와 서버가 붙인 `from`이 같은지 검사합니다. 땅 op는 `from`을 그대로 씁니다.
- 땅 구매는 **구매자 PC에서 먼저 돈을 빼고** op를 보내며, 경쟁에서 지면 환불합니다(`WorldOps.ApplyFor` → `LandPlotManager.RefundPending`).
- `GameSession.IsAuthority`는 `Mode != SessionMode.Client`, 즉 방장이거나 혼자일 때 true입니다.

### 시민·자동차 동기화
- `NPC/Citizen/CitizenSpawner.cs`: 야외 맵마다 8명(`PerMap`), 실내는 `Indoors` 표에 정의합니다. 번호, 이름, 대사, 외형, 시작점은 **(맵, 번호)의 순수 함수**라서 모든 PC가 같은 군중을 만듭니다. 맵 씬 안에 있어서 맵을 나가면 사라집니다.
- `NPC/Citizen/CitizenSync.cs`: `GameSession.IsAuthority`(방장)이면 시뮬레이션하고 0.2초마다 `world "citizens"`로 보냅니다. 다른 PC는 받은 위치로 보간합니다(`FollowTargets`, 6m 이상 차이 나면 순간이동). **3초 동안 그 맵 데이터가 안 오면(방장이 다른 맵에 있으면) 각자 로컬로 시뮬레이션합니다.** 그래서 같은 맵의 두 참가자가 같은 NPC를 서로 다른 위치에서 보는 버그가 있습니다. 패킷은 `{map, c:[{i,x,y,z,ry,s}]}`이고 목적지·상태는 없습니다.
- `NPC/Citizen/CitizenWalker.cs`: NavMeshAgent 기반이고 상태는 `Walk, Pause, Cross, ToSeat, Seated`, 원격 모드는 `SetProxy`입니다. `culled` 플래그가 있습니다.
- `NPC/Traffic/TrafficSync.cs`: 방장이 신호 시계와 차 위치를 0.2초마다 `world "traffic"`으로 보내고, 참가자는 프록시로 따라갑니다.

## 2. 1단계: 바로 작업 (맵·기능 완성과 무관)

나중에 할수록 고칠 곳이 늘어나는 기반 작업입니다. **1-1을 가장 먼저** 합니다(다른 팀원 작업에도 영향).

### 1-1. 행위자 ID 분리
- 목표: 공용 월드를 바꾸는 코드가 `GameSession.LocalPlayerId`를 직접 읽지 않고 **행위자 ID를 인자로** 받게 합니다. 그래야 이후 만드는 기능이 처음부터 봇도 쓸 수 있는 형태가 됩니다.
- `LocalPlayerId` 사용처(2026-10-13, Editor 제외, 파일별 횟수). 분류는 추정이므로 작업 시작 시 확인합니다.
  - **공용 월드 쓰기, 바꿀 대상**: `Economy/Property/LandPlotManager.cs`(3), `Economy/Property/PropertyRegistry.cs`(2), `Economy/SharedWriteGate.cs`(1, `ActorId`), `Gameplay/Sns/SnsManager.cs`(2), `Gameplay/Report/ReportManager.cs`(2), `Gameplay/PenaltyManager.cs`(1), `Gameplay/Traffic/SpeedCamera.cs`(1)
  - **내 PC 전용(UI·개인 저장), 그대로 둬도 될 가능성 큼**: `Core/Session/GameSession.cs`(4, 정의), `Gameplay/PersonalSave.cs`(2), `Gameplay/WorldSave.cs`(1), `Gameplay/Item/Book/*`(BookSaveService 1, LibraryCatalog 2, BookReader 11, LibraryDesk 8), `Gameplay/Phone/ReportApplication.cs`(2), `UI/ChatUIManager.cs`(1), `UI/Title/TitleFlow.cs`(1)
- 방법: 매니저의 공용 쓰기 메서드에 `actorId` 인자를 추가하고, 플레이어 UI 쪽 호출부에서 `GameSession.LocalPlayerId`를 넘깁니다. `SharedWriteGate.ActorId(fallback)`의 의미를 정리합니다.
- 완료 기준: 플레이 결과가 기존과 같습니다(혼자, 2인 방 모두). 공용 쓰기 경로에서 `LocalPlayerId`를 직접 읽는 곳이 없습니다.

### 1-2. `CharacterProfile` + `CharacterBody`
- `CharacterProfile`: `[Serializable]` 순수 데이터 클래스입니다.
  - 외형: 성별/기본 몸통, 키, 피부색, 옷 색(지금은 색, 모델이 바뀌면 머리·옷 ID)
  - 상태: 체력, 기력, 정신력(지금 stress)
  - 스탯: 지능, 매력, 체력스탯, 농사, 요리
  - 성향: AI 플레이어만 사용(2단계에서 추가)
- `CharacterBody`: Profile을 받아 몸통을 고르고 색과 키를 적용하는 컴포넌트 하나입니다. 플레이어, 시민, 원격 아바타가 같이 씁니다. "누가 조종하느냐"(키보드, 시민 AI, 봇 AI, 네트워크)는 지금처럼 별도 컴포넌트로 둡니다.
- 옮길 것: `PlayerStats`의 값은 Profile로 옮기되 기존 API(`Health`, `Add`, `Changed` 등)는 유지해 호출부를 덜 건드립니다. `DaldongnePlayerAppearance`와 `CitizenInfo.Dress`는 `CharacterBody`로 합칩니다. 시민은 지금처럼 시드로 Profile을 만들고, **바뀐 시민만 저장**합니다.
- 주의: 개인 저장(`PersonalSave`)의 기존 필드 이름이 바뀌면 옛 세이브의 값이 사라집니다. 저장 형식은 유지하거나 변환 코드를 둡니다.
- 완료 기준: 세 종류가 같은 구조로 표시되고 기존 세이브가 열립니다.

### 1-3. 원격 아바타 외형 전달
- 방에 들어갈 때(그리고 외형이 바뀔 때) Profile의 외형 부분만 보냅니다. 수백 바이트입니다. `msg`나 `pos`에 붙이는 방법 중 하나를 고릅니다. 늦게 들어온 사람도 받아야 하므로 입장 시점 처리가 필요합니다.
- `NetPlayerSync`가 원격 아바타를 만들 때 `CharacterBody`에 적용합니다.
- 완료 기준: 상대 화면에 내 성별·색·키가 보입니다.

### 1-4. 시민·자동차 맵 담당 전환
- **서버 변경 필요**: 지금 `world`는 방장만 보낼 수 있습니다(`Server/src/rooms.ts` `relayWorld`). 맵 담당이 보낼 수 있게 바꿉니다. 방법은 둘 중 하나입니다.
  - (권장) 서버는 그대로 중계하되 방 멤버 누구나 `world`를 보낼 수 있게 하고, **받는 쪽이 "그 맵의 담당이 보낸 것만" 적용**합니다. 서버가 `from`을 붙여 주도록 합니다(지금 `world` 브로드캐스트에는 `from`이 없음). `world`에 `pos`처럼 개수 제한 버킷을 추가합니다.
  - 서버가 맵별 담당을 직접 관리하는 방법은 서버가 무거워지므로 피합니다.
  - Node(`src/`)와 Worker(`worker/`)가 같은 `rooms.ts`/`protocol.ts`를 쓰는지 확인하고 둘 다 맞춥니다.
- 담당 정하기: 각 PC가 `pos` 메시지로 모든 사람의 맵을 알고 있으므로, **"그 맵에 있는 사람 중 계정 ID가 가장 작은 사람"**처럼 결정적인 규칙으로 정하면 서버 없이도 모두 같은 담당을 고릅니다. 자기 자신도 후보에 넣습니다. 혼자면 항상 자기가 담당입니다.
- `CitizenSync`, `TrafficSync`의 `GameSession.IsAuthority` 판정을 "내가 이 맵 담당인가"로 바꿉니다. **3초 뒤 로컬 시뮬레이션으로 넘어가는 폴백(`StaleSeconds`)은 없앱니다**(이게 서로 다르게 보이는 원인).
- 담당 교대가 매끄럽게: 패킷에 **목적지와 상태**(Walk/Pause/Cross/ToSeat/Seated, 앉을 자리)를 추가합니다. 새 담당은 이미 보간해서 보고 있던 위치에서 그 목적지로 이어서 시뮬레이션합니다(`SetProxy(false)` 시 목적지 복원). 담당이 갑자기 끊긴 경우만 0.5초 정도 멈칫할 수 있습니다.
- 자동차 신호 시계(`TrafficSignal.Clock`/`TimeOffset`)도 맵 담당 기준으로 맞춥니다.
- 완료 기준: 방장이 다른 맵에 있어도 같은 맵의 두 사람이 같은 NPC 위치를 봅니다. 담당이 맵을 나가도 NPC가 튀지 않습니다. 2 PC로 확인합니다.

### 1-4b. 방 채팅
- 지금 채팅은 **네트워크로 나가지 않습니다.** `UI/ChatUIManager.cs`의 `SendChatMessage`는 내 채팅창과 말풍선에만 표시합니다.
- 기존 메시지는 맞지 않습니다: `msg`는 참가자가 방장에게만 보낼 수 있고, `op`는 서버에 기록되며 초당 10개 제한을 경제 행동과 나눠 씁니다.
- 서버(`Server/src/protocol.ts`, `src/rooms.ts`, Worker 쪽도)에 `chat` 종류를 추가합니다: 방 멤버 누구나, 방 전체로, 저장 안 함, 별도 개수 제한, 서버가 `from`을 붙임. Unity는 `NetSession`에 송수신을 추가하고 `ChatUIManager`가 받은 메시지를 보낸 사람 이름으로 표시합니다.
- 나중에 봇 대사도 이 채널로 보냅니다(방장 PC가 봇 이름으로 전송, 서버가 방장일 때만 대리 이름 허용).
- `ChatUIManager.cs`의 한글 주석이 EUC-KR로 저장되어 깨져 보입니다. 수정할 때 UTF-8로 바꿉니다.
- 완료 기준: 방장·참가자 누구의 채팅이든 모두에게 보입니다.

### 1-5. 기본 보안 보강
- `WorldOps` 적용 전에 잔액, 소유권, 수량 검사를 넓혀 조건이 안 맞는 op는 모든 PC에서 똑같이 거절되게 합니다.
- 서버 개수 제한은 `op`(10/초), `pos`, `msg`, `state`에 **이미 있습니다.** `world`에만 없으니 1-4에서 같이 추가합니다.
- 완료 기준: 조작된 op(남의 땅 등록, 없는 돈으로 구매)가 모든 PC에서 거절됩니다.

거래, 주식, 땅, 회사 기능이 어느 정도 확정된 뒤에 합니다.

| 순서 | 작업 | 내용 |
| --- | --- | --- |
| 2-1 | 봇 대리 실행 op | op 인자에 대리 행위자 필드를 추가합니다. **`from`이 현재 방장일 때만** 봇 ID(`bot:1` 형식, 계정 ID와 겹치지 않게)로 적용하고, 그 외에는 `WrongActor`로 거절합니다. `ActorMatches`에 반영합니다. |
| 2-2 | op 개수 제한 대응 | 봇 op는 전부 방장 연결로 나가므로 **방장의 op 10/초를 방장 본인과 봇 20명이 나눠 씁니다.** 봇 판단을 몇 초 간격으로 분산하고, 필요하면 여러 봇 행동을 op 하나로 묶습니다(`bot.batch`). 서버 한도를 올리는 건 마지막 수단입니다. |
| 2-3 | 봇 데이터 | 봇마다 `CharacterProfile`(성향 포함), 목표 타입, 은행 계좌·지갑 현금·인벤토리, 이동 기록(출발지, 목적지, 출발 시각, 도착 예정 시각, 현재 맵), 관계 점수 표를 **월드 스냅샷**(`WorldSave`)에 넣습니다. 512KB 한도 안에 드는지 확인하고, 관계 점수는 0이 아닌 값만 저장합니다. 땅 구매처럼 "먼저 돈을 빼고 지면 환불"하는 흐름은 봇 계좌에도 똑같이 적용합니다. |
| 2-4 | 백단 시뮬레이션 | 사람 없는 맵의 봇은 이동 기록으로만 움직입니다(몸체·NavMesh 없음). 판단은 2-5초마다 하고 봇마다 시점을 흩어 한 프레임에 몰리지 않게 합니다. |
| 2-5 | 맵 입장 시 생성 | 사람이 맵에 들어오면 그 맵 담당이 봇 몸체를 만듭니다. 위치는 지금 게임 시각 기준으로 이동 기록에서 계산합니다: 건물 안이면 실내, 이동 중이면 경로 위입니다. 맵 경계를 넘어오는 봇은 입구·길 끝에서 걸어 들어옵니다. 시민 NPC도 일과표를 시간으로 계산하면 같은 방식이 됩니다. |
| 2-6 | 몸체 ↔ 데이터 전환 | 맵에서 마지막 사람이 나가면 몸체를 지우고, 마지막 위치와 목적지를 이동 기록으로 되돌립니다. 봇 몸체 위치는 시민과 같은 `world` 패킷 방식(맵 담당이 0.2초마다)으로 보냅니다. |
| 2-7 | 방 채우기 | 실제 인원이 정한 수보다 적으면 봇으로 채우고, 사람이 들어오면 봇이 빠집니다(카트라이더 방식). 빠진 봇의 재산 처리 규칙을 정합니다. |

## 5. 방장 PC 부담 줄이기

봇 판단(숫자 계산)은 가볍습니다. **무거운 건 몸체(렌더링, 스키닝, 길찾기, 애니메이션)**입니다. 원칙과 방법은 아래와 같습니다.

### 구조로 줄이기 (1-4, 2-4에서 같이 적용)
- **몸체는 실제 사람이 있는 맵에만** 만듭니다. 사람 없는 맵은 숫자로만 시뮬레이션합니다.
- **맵 담당이 몸체를 나눠 맡습니다.** 방장은 자기 맵의 몸체와 전체 봇 두뇌만 맡고, 다른 맵의 몸체는 그 맵에 있는 사람 PC가 맡습니다.
- 봇 두뇌는 `MonoBehaviour`가 아니라 **일반 C# 객체 목록**으로 두고, 관리자 하나가 몇 초 간격으로 차례대로 돌립니다(봇마다 `Update` 금지). 한 프레임에 몇 명씩만 판단합니다.
- 봇이 시민 NPC처럼 맵 씬에 묶이지 않게, 두뇌는 `DontDestroyOnLoad` 쪽 또는 순수 데이터에 두고 몸체만 맵 씬에 만듭니다.

### 렌더링·애니메이션
- **플레이어 모델이 22만 폴리곤**입니다. 봇·원격 아바타·시민에 그대로 쓰면 안 됩니다. 봇과 원격 아바타는 시민용 가벼운 메시를 쓰거나 LOD(가까울 때만 고해상도)를 둡니다. 모델 교체 시 목표는 1~2만 폴리곤입니다(6절).
- 화면 밖 캐릭터는 애니메이션·스키닝을 멈춥니다(`SkinnedMeshRenderer.updateWhenOffscreen = false`, 애니메이터 컬링). `CitizenWalker`에 이미 `culled` 플래그가 있으니 같은 방식을 봇에도 씁니다.
- 멀리 있는 캐릭터는 이름표, 그림자, 업데이트 빈도를 줄입니다.

### 길찾기(NavMesh)
- 경로 재계산 빈도를 제한합니다(목적지 바뀔 때만, 또는 몇 초마다).
- 멀리 있는 에이전트는 회피 품질(`obstacleAvoidanceType`)을 낮춥니다.
- 맵당 동시에 걷는 봇 수에 상한을 둡니다. 나머지는 건물 안이나 앉은 상태로 둡니다.

### 네트워크·저장
- 봇 위치는 봇마다 따로 보내지 않고 **맵 하나당 패킷 하나**로 묶습니다(시민 패킷과 합쳐도 됨). 소수 둘째 자리 반올림은 지금처럼 하고, 안 움직인 봇은 뺍니다. 메시지 한 개 8KB 한도를 넘지 않게 확인합니다.
- op는 2-2처럼 분산·묶음 처리합니다.
- 월드 스냅샷(10초마다, 최대 512KB)에 봇 데이터를 넣을 때는 계산으로 다시 만들 수 있는 값(시드로 나오는 외형 등)은 빼고 바뀐 값만 넣습니다.
- 매 틱 `JsonUtility` 직렬화와 리스트 생성으로 생기는 GC를 줄입니다(리스트 재사용).

### 사양 비교 (추정, 실측 전)
**시뮬레이션은 담당 PC만 하지만 렌더링은 그 맵을 보는 모든 PC가 합니다.** 봇이 많은 맵에 있으면 방장만이 아니라 모두가 무거워집니다.

| | 스타듀밸리 | 팰월드(방장 PC 코옵) | 우리 · AI 없음 | 우리 · AI 20명 |
| --- | --- | --- | --- | --- |
| 방장이 하는 일 | 월드 전체 시뮬레이션 | 월드 + 모든 팰 AI·전투·물리 | 시계, 스냅샷, 자기 맵 시민·자동차 | 왼쪽 + 봇 두뇌 + 자기 맵 봇 몸체 |
| 방장 추가 부담 | 거의 없음 | 큼(대규모는 전용 서버 권장) | 작음 | 중간 |
| 방장 사양 | 거의 무관 | 확실히 더 좋아야 함 | 참가자와 비슷하면 충분 | 참가자보다 한 단계 위면 안정 |

- AI 20명은 5절 최적화를 했을 때 팰월드보다 가볍습니다. **최적화를 안 하면 22만 폴리곤 모델 때문에 팰월드보다 나빠질 수 있습니다.** 모델 경량화가 사양을 결정하는 가장 큰 요소입니다.
- AI 없음에서도 10초마다 최대 512KB JSON 스냅샷을 만들 때 방장 화면이 순간 끊기는지 확인합니다.

### 측정 (작업 후 반드시)
- Unity Profiler로 봇 0명 / 10명 / 20명일 때 방장 PC의 프레임 시간, GC, 스키닝 비용을 비교합니다.
- 방장 프레임이 떨어지면 모두의 동기화가 같이 느려지므로(방장이 시계·스냅샷·봇 두뇌 담당), **방장 프레임이 기준선**입니다.

## 7. 보안 (현재 신뢰 모델)

| 막혀 있음 | 막히지 않음 (구조 한계) |
| --- | --- |

## 8. 확인할 것

| 항목 | 내용 |
| --- | --- |
| 실제 딜레이 | 두 PC로 접속해 핑과 NPC 위치 차이를 로그로 측정합니다. 예상은 위치가 핑 + 0.1~0.3초, 경제 행동이 핑만큼입니다. |
| 서버 위치 | 해외 무료 호스팅이면 핑이 200~300ms까지 오를 수 있습니다. |
| Worker 무료 한도 | Cloudflare Worker(Durable Object)로 배포하면 WebSocket 메시지 수가 무료 한도에 걸릴 수 있습니다. 맵 담당이 늘면 `world` 메시지도 늘어나므로, 배포 전에 현재 요금표와 무료 한도를 확인합니다. 로컬 Node + 터널은 이 걱정이 없습니다. |
| 방장 PC 부하 | 5절의 측정을 합니다. |
| 스냅샷 크기 | 봇 20명 데이터를 넣은 월드 스냅샷이 512KB 안에 드는지 확인합니다. |
